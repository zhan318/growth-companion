# 简历 / 面试素材：成长智伴的评测体系与检索优化

> 数据截至 2026-11-11，来源：`eval/reports/`（retrieval-report.md / e2e-report.md / answers 存档）

## 一、简历上一段话怎么写（项目描述里评测部分）

> 自建三层 RAG/Agent 评测体系（pytest 单测 78 例 / 检索层 Recall@K / 生成层 LLM-as-a-Judge / e2e 工具路由评测 36 例），
> 以评测驱动定位并修复检索瓶颈：中文语义检索命中率由 4.8% 提升至 66.7%（替换英文 embedding 为 BGE 中文模型），
> 引入 Cross-Encoder 精排后 RRF 融合命中率 66.7% → 71.4%；Agent 工具路由准确率 97.2%（36 例），答案质量分 90.3%。

## 二、三层评测体系（面试讲"怎么保证效果"）

| 层 | 回答什么 | 方法 | 成本 |
|---|---|---|---|
| 单元测试 | 逻辑对不对 | pytest，13 文件 78 用例 | 秒级 |
| 检索层评测 | 检索准不准 | golden 集 25 条，代码算 Recall@K / 命中率，**零 LLM 调用** | 免费、可回归 |
| 生成层评测 | 答得好不好 | LLM-as-a-Judge（指标对齐 RAGAS：faithfulness/relevancy/correctness/hallucination） | 每条 2 次调用 |
| e2e 路由评测 | Agent 该调的工具调了没有 | 进程内直调 Agent.run()，日志捕获工具调用序列 vs 预期，含 not_in_kb 防幻觉项 | 每条 1-3 次调用 |

**为什么分层**：检索差和生成差是两码事，混在一起测无法定位瓶颈。分层后能精确回答
"是没检到（检索层）、检到了没答好（生成层）、还是根本没去检（路由层）"。

## 三、检索优化过程（面试讲"发现问题→定位→修复"的完整闭环）

| 版本 | dense 命中率 | RRF 融合命中率 | 关键改动 |
|---|---|---|---|
| v0（9-12 基线） | 4.8% | 66.7% | Chroma 内置 all-MiniLM-L6-v2（英文优化），中文 query 语义检索几乎失效，全靠 BM25 字面匹配硬撑 |
| v1（换中文 embedding） | **66.7%** | 61.9% | BAAI/bge-small-zh-v1.5（512 维，本地 CPU），dense 翻 14 倍自力更生；融合反而降——BM25 词面匹配把 dense 正确命中挤出 top-k |
| v2（+Cross-Encoder 精排） | 66.7% | **71.4%** | bge-reranker-base 对宽召回候选重排，纠正"词面匹配 ≠ 真正相关" |

**每一步都是评测数据驱动的决策**，不是拍脑袋换模型：
- v0→v1：检索层报告显示 dense 4.8%，根因是英文模型对中文失效
- v1 融合下降暴露 RRF 只看排名不看内容的缺陷 → 正是引入精排的理由
- not_in_kb 越界检出始终 0/4（防幻觉底线未破）

**技术细节可展开**：BGE 官方最佳实践——query 侧加检索指令前缀 + 向量归一化；
换 embedding 维度变化（384→512）必须全量重建索引（272 文件 / 1349 切片，126s）。

## 四、e2e 路由评测的独特点（多数候选人没有的部分）

传统 RAG 评测只测检索准确率；**Agentic RAG 还要测路由准确率**——检索作为工具被模型自主调用，检索再好，模型不调就等于没有。

36 条真机评测（25 条 golden RAG + 11 条功能路由），最终干净环境结果：
- **路由总命中率 97.2%**：工具路由 100%、闲聊不误调 100%、笔记读写 100%、RAG 问题 21/21
- 唯一 MISS：库外实时问题（世界杯冠军）模型自主选择联网搜索而非知识库检索——预期定义过严，实际是合理路由
- 答案质量分 90.3%（白盒判分：correct 31 / partial 3 / 其他 2），剩余扣分来自判分边界与沙盒外部 API 超时
- 端到端耗时 p50 29.7s（检索变准后 Agent 不再反复试错调工具，旧版最多单题调 9 次工具）

**评测体系本身经历三轮迭代，每一轮都修掉一个评测方法论 bug（面试重点素材）**：
1. 第一轮：judge 黑盒判分（只看问答）——抽查 5 条低分 4 条误判（如工具调用成功却被判"没调"）→ 改白盒（喂入日志捕获的工具调用序列）
2. 第二轮：路由数据被历史污染——清理时漏清 SQLite 会话历史，Agent 加载了上一轮对话说"你问过一遍"直接复用旧答案 → 补全会话清理，重跑
3. 第三轮（干净环境）：路由 97.2%、质量分 90.3%，数据可信

**测试基建的实现要点**：不改项目代码，通过 logging.Handler 捕获 agent logger 的工具执行记录；
每条用例独立 session 隔离，跑完自动清理向量记忆、SQLite 会话与测试文件。

## 五、评测发现的真实问题（面试讲"你的系统有什么不足"）

1. **工具调用抑制**：简单知识题模型凭参数知识直接答，绕过 RAG（2/21）——解法方向：prompt 约束 / 工具描述强化 / 检索前置路由
2. **golden 集预期文档标注过窄**：多条问题期望唯一"大杂烩"笔记，检索到的专业笔记内容更对口却判 MISS——71.4% 是保守下界
3. **LLM-as-a-Judge 黑盒偏差**：第一版 judge 看不到工具调用记录，抽查 5 条低分 4 条误判 → 改为白盒（喂入日志捕获的调用序列）
4. **写库行为越界**：库外写作请求触发 write_obsidian_note 直接写盘——产品上应有写前确认机制

主动说出局限 + 给出解法方向，比被面试官挑出来强一个量级。

## 六、可复现命令

```bash

.venv/Scripts/python eval/eval_retrieval.py --k 3

.venv/Scripts/python eval/eval_generation.py --limit 10

.venv/Scripts/python eval/eval_e2e.py [--only tool|rag|chat] [--no-judge]
```
