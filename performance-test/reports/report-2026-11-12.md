# 成长智伴 · 并发性能测试报告

> 测试日期：2026-11-12　|　测试对象：ReAct Agent 主链路 `/chat`
> 对照基线：8 月旧数据（优化前代码，已过时，仅作历史参考）

## 一、测试目的与方法

11-11 大版本把检索层整个换掉（embedding `all-MiniLM-L6-v2(384维)` → `bge-small-zh-v1.5(512维)`，检索从纯 dense 升级为 **dense + BM25 RRF 融合 + bge-reranker-base 精排**），链路更重，8 月旧并发数据已不代表现状，故重跑。

**两种模式分开测，隔离变量：**

| 模式 | LLM | 目的 |
|---|---|---|
| 真打 glm | 真实智谱 `glm-4.5-air` | 测"真实端到端"能力，暴露 LLM 侧瓶颈 |
| mock | 本地 mock（150ms 延迟） | 测"后端代码自身"能力，隔离 LLM 变量 |

**环境**：外部工具（天气/热搜/搜索/GitHub）一律走本地 mock；存储隔离（`MEMORY_DB_PATH`/`VECTOR_MEMORY_DIR` 指临时目录，压测消息不污染真实历史）；Obsidian 检索走**真实 vault + 真实向量索引**（测真实 reranker 负载）。

**场景**：单工具基线（1 用户 3 分钟）+ 并发阶梯 1/5/10/30/50（各 90 秒），对齐 8 月口径。

---

## 二、真打 glm 结果

### 单工具基线（1 用户 3 分钟）✅

| 指标 | 值 |
|---|---|
| 请求数 | 7 次，0 失败 |
| 平均延迟 | 15.0s |
| 中位数 / P95 | 7.8s / 44s |

真打 glm 的单请求延迟约 8–15s（含 LLM 1–2 轮 + 工具调用）。

### 并发阶梯 ❌ 全部失败

1/5/10/30/50 五档在 90 秒内**均 0 个请求完成**。后端日志实锤根因：

- 大量 `Retrying request to /chat/completions`（glm 返回 429 限流，openai client 自动重试）
- 请求响应时间暴涨到 200 秒+（`POST /chat → 500 (213823ms)`）
- 大量 500（超时）堆积，并拖累 `get_hotlist`/`web_search` 工具也被挤超时

**发现①（LLM 层瓶颈）**：`glm-4.5-air` 单个 API key 有 QPM/并发限制，并发一上来即触发限流；而 openai client 面对 429 是**无限重试**，重试占满线程池 → 请求雪崩。**根因是"后端缺 LLM 限流降级"**（无快速失败、无指数退避、无多 key 轮询）。

## 三、mock 结果（隔离 LLM，测后端自身）

### 单工具基线（1 用户 3 分钟）✅

| 指标 | `/chat` | `/chat-multi-tool` |
|---|---|---|
| 请求数 | 15 次 | 6 次 |
| 中位数 | 6.4s | 7.8s |
| 失败 | 0 | 0 |

### 并发阶梯（各 90 秒）

| 并发 | 完成请求数 | 平均延迟 | 中位数 | P95 | 结论 |
|---|---|---|---|---|---|
| 1u | 9 | 6.3s | 6.3s | 12s | 正常 |
| 5u | 15 | 24s | 24s | 27s | 延迟升 ~4x |
| 10u | 10 | 58–62s | 58s | 60s | 吞吐反降，进入饱和 |
| 30u | 0 | — | — | — | 完全卡死 |
| 50u | 0 | — | — | — | 完全卡死 |

**发现②（检索层瓶颈）**：reranker 是 CPU 密集计算，`asyncio.to_thread` 走 Python 默认线程池（约 32 线程上限）。**~10 并发即饱和，30 并发起请求堆积到 90 秒内无法完成**。这正是 8 月"异步化"后遗留的隐性瓶颈——事件循环不卡了，但 CPU 密集的 reranker 把线程池打满，成了新的天花板。

---

## 四、结论

后端并发画像现在完整了，两个瓶颈分层清晰：

1. **LLM 层**：真打单一 glm key 时，glm 限流是天花板；后端缺降级导致雪崩。
2. **检索层**：reranker CPU 密集 + 默认线程池，~10 并发饱和，30 并发卡死。

单请求（1 并发）延迟：真打 8–15s（glm 主导）/ mock 6.5s（reranker 主导）。

## 五、改进建议（按优先级）

| 优先级 | 方向 | 做法 |
|---|---|---|
| P0 | LLM 限流降级 | openai client 限 `max_retries` + 指数退避；失败快速返回友好错误；预留多 key 轮询 |
| P0 | reranker 并发闸门 | 给精排加 `asyncio.Semaphore` 限流，超限走 RRF 融合结果兜底（不精排） |
| P1 | reranker 结果缓存 | 同 query 短时间窗复用，降低重复 CPU 计算 |
| P1 | reranker 加速 | 换 ONNX 量化（`optimum`/`onnxruntime`）或更轻的精排模型 |
| P2 | 检索降级开关 | 高负载时自动关闭 reranker，退化为 dense+BM25 RRF |
